# Runtime OS application candidate images

This directory packages the complete PostgreSQL deployment: API, MCP, News Runtime, Node Coding Agent, PostgreSQL, Redis, TLS-enabled OpenSearch and its authenticated security initialization. Infrastructure is included by default. PostgreSQL/Redis health and successful OpenSearch initialization gate Java startup; News → MCP → API → Coding/sidecar → gateway provides an acyclic startup order. See [the Chinese maintenance commands and dependency inventory](../../DOCKER-MAINTENANCE.zh-CN.md) and [deployment.env.example](deployment.env.example) for setup, per-service Docker commands, secrets, certificates and backups. Node stays on an internal network without database/MCP access. A small Nginx sidecar exposes Node on API loopback, as required by `ClineCodingAdapter`. The gateway exposes authenticated API/MCP routes on ports 18100/18101; internal callbacks and actuator routes return 404. Application ports 18180/18190 remain on host loopback.

`/monitor` and `/monitor/` route to Coding Agent's monitor, not Java's static resources. The sidecar exposes a separate monitor-only listener on port 8792 inside API's network namespace; gateway forwards only monitor UI/API namespaces to it. Runtime execution remains on loopback 8791. Monitor login retains its independent token and same-origin cookie checks. Supply `CODING_MONITOR_TOKEN_FILE` separately from the dispatch secret; monitor history uses its own persistent volume. Host configuration, keys and policies should live under `STAGE_ROOT/config`, with identical container-side paths; copying a file alone does not update an existing bind mount, so verified container recreation is required when the source path changes. Keep persisted data mounts unchanged.

Build on a Linux/amd64 Docker daemon from the repository root. Supply the Docker CLI binary from a trusted Docker installation compatible with the destination daemon; `Dockerfile.mcp` copies only that CLI, since the MCP service launches the existing Python Sandbox through the host Docker socket.

```powershell
./deploy/docker/application/build-images.ps1 -DockerCliPath ./target/docker-application-build/mcp/docker -Tag 9cc5ac8f-stage
```

The script installs frontend dependencies from the lockfile, builds the web application into `target/docker-application-build/frontend`, and packages that matching output into the API JAR without rewriting versioned static sources. The `container.image=true` Maven profile excludes local key files, licenses, private PEM files and `.env` files from first-party JARs; existing local files are retained. It checks local index resources and scans both application JARs and nested first-party libraries for deployment secret files before building all four images, pulling the pinned Nginx proxy image, and exporting one archive with a SHA-256 digest. `-SkipMaven` reuses existing JARs but still performs both checks; a successful backend-only build alone does not establish image completeness. These filename checks are not a general secret-content scan. The Docker CLI is an explicit build input and must be recorded alongside that digest. Deployment credentials and licenses must come from the external mounts and environment files described below.

On the destination, prepare private `api.env`, `mcp.env`, `news.env` and `deployment.env` using the example and maintenance guide. The new PostgreSQL service creates separate API/MCP databases only on an empty volume. API/MCP use service DNS and file-backed config-tree passwords. The OpenSearch CA must be installed in the configured Java truststore while preserving public CAs. Copy both proxy configs to `$STAGE_ROOT/config`. The Node secret must match API's and be readable by UID 1000/GID 32101 (for example root:32101, mode 0640). This is a complete new-install topology: existing external databases/indexes require a reviewed backup/restore and connection migration before adopting it. Do not apply it to an existing server expecting automatic data adoption. Keep the repository layout, because SQL and support-script mounts are relative to this Compose file. Run from the repository root:

```bash
docker load -i /opt/runtime-os-docker-stage/images/runtime-os-app-stage-9cc5ac8f.tar
docker compose --env-file /opt/runtime-os-docker-stage/config/deployment.env \
  -f deploy/docker/application/compose.yaml config -q
docker compose --env-file /opt/runtime-os-docker-stage/config/deployment.env \
  -f deploy/docker/application/compose.yaml up -d --no-build --wait --wait-timeout 600
```

Copy `public-gateway.conf` alongside `node-proxy.conf` under `$STAGE_ROOT/config`. Run `sh host-license-identity.sh HOST_NIC` on the destination host and add its output to `deployment.env`. `MCP_HOST_MAC_FILE` must name the host device NIC's `/sys/class/net/HOST_NIC/address` file. Compose mounts that single sysfs file read-only at `/run/license/host-mac`, with automatic host-path creation disabled; no host networking or extra container privileges are needed. MCP's `chatchat.license.host-mac-file` setting selects this identity exclusively. A missing or invalid configured identity fails closed, with no fallback to container MACs. The machine code and MAC-based signed license remain stable across container recreation. Bare-host deployments without this setting retain existing NIC discovery.

Use the existing signed license when it already matches the selected host NIC. Otherwise request a license for that host MAC through the license center while preserving the authorized entitlements. Verify `/api/v1/license/status` reports the host MAC and `VALID` after two container recreations. Changing hosts or the licensed host NIC requires a license change; changing the container MAC does not. On a virtual machine this identifies the VM's installed device NIC, not the hypervisor's physical adapter. Never bake the license, signing key or license-center credentials into an image.

The current init SQL can trail entity changes. An isolated candidate may use Hibernate `update` once to bootstrap its empty databases, then restart with `SPRING_JPA_HIBERNATE_DDL_AUTO=validate`. Production must use reviewed migrations. The candidate requires a published Python environment in its own MCP database before Coding Agent analysis can run. MCP has the host Docker socket. Do not route production traffic until the full Runtime OS gate and live QA/data-analysis acceptance pass. `docker compose ... down` now also stops this stack's PostgreSQL, Redis and OpenSearch; their named volumes and application bind data remain. Do not use `down -v` for upgrades.

The 2026-10-17 candidate returned `SERVER_MISMATCH` after loading the host license inside Docker. The initial 2026-10-18 container-MAC issuance receipt remains in the remote private evidence directory. The deployment now uses host NIC identity so application upgrades do not require container-specific reissuance. Deployment verification evidence must distinguish this host-identity configuration from the earlier container-MAC candidate; licensing alone does not certify the Runtime OS acceptance gate.


News Runtime and existing data directories
------------------------------------------

Set `NEWS_IMAGE=runtime-os-news:TAG`, `NEWS_DATA_DIR` and `NEWS_CONFIG_DIR` to the existing News installation directories. Create `$STAGE_ROOT/config/news.env` with the existing database/profile and service settings. For the current H2 installation use `SPRING_PROFILES_ACTIVE=h2`; the existing H2 file and internal credential key stay on the host. News listens only on the Compose control network at `news:8091`; MCP routes its existing signed News client to that address. News calls MCP at `http://mcp:8090`. Configuration is mounted read-only. Existing embedded Temporal mode is memory-only; mounting the H2 database does not make Temporal workflow history durable. External durable Temporal remains a separate deployment choice.

Set the required `API_DATA_DIR=/opt/chatchat-1.0.0-SNAPSHOT/data` and `MCP_DATA_DIR=/opt/chatchat-mcp-server-1.0.0-SNAPSHOT/data` when reusing the existing host installations. Each service mounts its own directory at `/srv/app/data`; do not share one directory between services. There is no implicit replacement data directory. Missing primary data/config paths fail instead of creating an empty replacement. Stop other processes using those files and back up the directories before switching mounts. These file mounts do not migrate or select PostgreSQL databases: the existing `api.env` and `mcp.env` still choose those databases.

Conversation history needs three consistent stores: PostgreSQL session/message indexes and task events; the API `data/chat-rocksdb` keys; and the configured OpenSearch chat-detail index for externally stored bodies. UI artifact files under `data/ui-artifacts` also need their PostgreSQL metadata. The document-search index is a separate setting from the chat-detail index. Keep the old chat-detail index readable during upgrades. `CHAT_EXTERNAL_TEXT_ENABLED` defaults to true; legacy inline bodies remain readable, with automatic on-read conversion disabled in this deployment. API and MCP receive 60 seconds for graceful shutdown so embedded stores can close before replacement. PostgreSQL and OpenSearch require their own durable volumes and backups; application bind mounts alone do not back up either service.

When the container uses a new database, merge archived history without replacing current sessions or unrelated model/authorization configuration:

```bash
python3 scripts/migrate-container-conversation-history.py \
  --source OLD_DATABASE --target CONTAINER_DATABASE --backup-dir /private/history-backups
# Review the dry run, then repeat with --apply.
```

The migration checks compatible schemas, verified object identities and terminal tasks, creates a private destination backup, and imports eight history tables in one transaction with existing keys preserved. Repeating it inserts zero existing records. It leaves the source database unchanged. Back up all three stores together; retain private export/import logs, which may contain business data. Recovering SQL indexes does not recreate deleted bodies.

The history APIs merge the authenticated user's stable ID and the legacy username through `ObjectAccessService.ownerAliases`, including search and pagination. Tenant scope and the platform/API source-channel distinction remain enforced. A username that collides with another principal's stable ID is excluded. No ownership fields are rewritten. A partially restored conversation exposes `missingMessageCount`; the page retains available messages, shows the gap and reloads the detail on reopen. The chat component also restores its initial conversation prop immediately: with asynchronous workspace loading, history details can arrive before the component mounts, and a change-only watcher would otherwise leave the restored view empty. The initial workspace load retains a sidebar selection made while its manifest was in flight; subsequent workspace switches retain their separate saved contexts. Cancelled messages and their recorded execution steps keep their terminal state. Empty header trees fall back to the persisted message analysis-node and selection metadata to restore analysis branches.

For missing bodies, `prepare-conversation-body-recovery.py` and `ChatHistoryBodyRecovery.java` provide an audited offline repair. Export indexes, use the Java `scan` with the deployed RocksDB/Jackson libraries, then prepare candidates from persisted single-turn task responses. Stop the API, copy the closed RocksDB directory, and apply the reviewed candidates. The immutable original key supplies its timestamp because historical SQL migrations may have shifted index time zones. The Java repair checks tenant, owner, session, message, role and key identities; writes are atomic and synchronous, and existing bodies/references win. Ambiguous multi-turn records and absent responses stay unresolved. No model is called and no analysis is rerun. Raw candidates, backups and unresolved identifiers must remain private. `deploy-session-persistence-stage.py` applies this API-only fix to the isolated stage, preserving its current bind source and unrelated containers, with configuration/image rollback on startup failure.

The Docker daemon must see Python paths at the same absolute host/container location. `MCP_PYTHON_WORKSPACE_ROOT` and `MCP_PYTHON_DATA_ROOT` default beneath `MCP_DATA_DIR`. Preserve their previous absolute paths explicitly during a data-root change if already published Python environments or archived operations reference them; both remain persistent host bind mounts.

The gateway redirects legacy Runtime URLs `/admin`, `/admin/` and `/admin/index.html` to the current application root. Runtime HTML uses `Cache-Control: no-store, max-age=0`; `/favicon.ico` redirects to the packaged SVG. MCP admin URLs on port 18101 remain unchanged. The frontend build must still pass `verify-web-assets.ps1`: redirecting an HTML entry point does not repair a JAR containing mismatched hashed assets. Refresh an already cached old page after this upgrade.

The API Maven `prepare-package` phase now also checks the copied frontend output automatically with `scripts/VerifyWebAssets.java` (JDK 17, no Node dependency). This check runs even with `-DskipTests`, `-Dfrontend.skip=true`, or the `backend-only` profile. Skipping Vite is safe only when a complete earlier frontend build exists: this repository ignores most generated assets, so a fresh checkout's tracked HTML is insufficient. Missing or empty entrypoint JS/CSS blocks packaging. Build with the normal frontend flow first, then verify the final JAR with `verify-web-assets.ps1`. Deployment acceptance must check the referenced resources and use a real browser to render both the login page and an authenticated workspace; an HTML HTTP 200 alone does not establish frontend availability.

Run `python deploy/docker/application/tests/test_application_deployment.py` with Docker available to validate real Compose expansion, existing-data bind semantics, News network routing and Nginx syntax.

Coding callbacks and promotion
-----------------------------

Compose uses service DNS identities instead of fixed API/Worker addresses. Configure `CODING_CALLBACK_URL`, `CODING_CALLBACK_ALLOWED_HOSTS`, `CODING_CALLBACK_ALLOWED_HOSTNAMES` and secret-file mounts together. Explicit legacy addresses remain available through `CODING_CALLBACK_ALLOWED_ADDRESSES`; the signed callback protocol is still required. After candidate creation or container recreation, run `restrict-coding-worker.sh` with the candidate's `CODING_WORKER_CONTAINER`, `CODING_API_CONTAINER` and `CODING_NETWORK`; it atomically replaces only its owned firewall rules using inspected addresses.

Set `CODING_FIREWALL_VALIDATE_ONLY=1` to validate the proposed rules with `iptables-restore --test` before applying them. The Node proxy resolves Worker DNS dynamically so container IP changes do not require an Nginx reload. The isolated deployment test reserves the previous address and verifies routing to a recreated Worker at a different address.

Before promoting prepared candidate routes, run `python3 scripts/verify-coding-callback.py --worker CANDIDATE --report /private/releases/RELEASE/callback.json --promote-gateway GATEWAY`. A signed protocol preflight and an unsigned 401 check must both pass before the script tests/reloads Nginx. Without `--promote-gateway` it only verifies. A failed candidate must not replace current traffic. This gate complements the existing deployment system; it does not create a second rollout manager. Historical dated release scripts are reproduction/rollback records and do not implement the new protocol gate. See [the architecture and measured validation scope](../../../docs/runtime-coding-stability-20261026.md) for compatibility flags and test evidence. `GATEWAY_TEST_IMAGE` selects an already installed gateway image for isolated deployment tests.
