# Agent Runtime 最低模型性能与部署要求

文档版本：1.0

生效日期：2026-08-06

适用范围：ChatChat Agent Runtime 的规划模型、计划修复模型、工具结果审查模型、最终综合模型和答案评审模型

## 1. 目的

本规范定义可接入 ChatChat Agent Runtime 的大语言模型最低能力、上下文、部署资源、推理服务和验收测试要求。

模型参数量只用于估算能力与部署成本，不作为生产准入结论。模型是否合格，最终以真实 Runtime 协议和业务无关基准测试结果为准。

## 2. 基本概念

模型参数量和上下文窗口是两个独立维度：

- **参数量**决定模型能够承载的知识、模式和推理能力上限，可类比为“大脑规模”；
- **上下文窗口**决定单次请求能够读取的 Prompt、历史、工具 Schema 和 Evidence 数量，可类比为“桌面能够摆放的资料”；
- **KV Cache**保存当前上下文的注意力状态，其显存消耗随上下文长度、并发数、模型层数和 KV 精度增长；
- **Evidence Store**保存完整工具证据，不等同于模型上下文，也不能用无限扩大上下文替代。

因此，一个 70B 模型可以只启用 32K 上下文，也可以支持 128K 或更长上下文；一个标称 900K 上下文的模型也不代表其复杂推理能力等同于 70B 模型。

## 3. 模型分级

| 模型档位 | 典型能力 | Runtime 定位 | 默认准入结论 |
| --- | --- | --- | --- |
| 7B～8B | 能调用工具、提取简单参数、完成简单总结；复杂判断和多步修复容易出错 | 开发联调、演示、低风险单工具任务 | 不作为生产默认模型 |
| 14B | 能完成常规工具调用和短计划，但复杂 Evidence 冲突判断仍可能不稳定 | 受控场景最低可用模型 | 通过完整测试后可限定使用 |
| 30B～32B | 规划、工具选择、参数恢复和证据综合能力较好 | 通用生产基线 | 推荐生产最低档 |
| 70B～72B | 长任务、复杂业务语义、因果链、计划调整和多工具协作更稳定 | 高复杂度、关键业务任务 | 推荐增强档 |

参数越大不代表所有指标都更好。70B 模型通常具有更强的推理和规划能力，但也带来更高显存占用、更慢首 Token 延迟、更低并发和更高部署成本。量化质量、训练数据、长上下文训练方式、工具调用训练和服务实现都可能改变实际表现。

任何 7B、14B 或其他小模型，只要通过本规范全部生产门禁，也可以被限定准入；任何 70B 模型未通过门禁，都不得仅凭参数规模投入生产。

## 4. 强制能力要求

### 4.1 指令与协议

模型必须：

1. 正确遵循 System、用户请求、工作流快照和 Runtime 协议的优先级；
2. 稳定输出合法 JSON，正确处理嵌套对象、数组、布尔值、空值和 Unicode；
3. 不在 JSON 前后附加无法解析的解释文字；
4. 在协议校验失败后，能够根据错误信息修复输出；
5. 不伪造工具、工具参数、执行状态、URL、证据标识或调用结果；
6. 支持中文任务理解，并能够保留英文工具名、字段名和枚举值；
7. 支持当前部署使用的 OpenAI-compatible 或已适配的 DashScope 协议。

### 4.2 工具调用与规划

模型必须能够：

- 从动态工具清单中选择满足用户目标的工具；
- 严格按 Tool Schema 生成参数，不编造 Schema 外字段；
- 区分工具发现、模板选择、模板执行和最终分析；
- 生成无环、依赖正确且节点完整的候选 DAG；
- 在工具失败、证据不足或 Reviewer 不满意时提出有界修复计划；
- 识别已经完成的步骤，不无理由重复执行；
- 在仍有必需节点未完成时不提前输出最终答案；
- 遵守 Runtime 给出的权限、安全、重试、幂等和执行预算。

### 4.3 Evidence 分析

模型必须：

- 区分工具调用成功与用户目标已经满足；
- 区分完整证据、压缩摘要、预览截断和证据外置引用；
- 区分事实、推断、假设、缺失和冲突；
- 将 `evidenceCoverage.returnedEvidenceTypes` 仅作为返回数据说明；
- 由模型结合目标事实、标准参考和用户要求判断结论，不把 coverage 描述当作符合性裁决；
- 在证据不足时明确说明限制，不通过补写常识伪造结论；
- 在部分节点失败但仍有有效证据时交付部分结果；
- 让最终答案中的关键事实能够追溯到用户输入或工具 Evidence。

### 4.4 长上下文

模型最低应支持 128K tokens 上下文，并在接近上限时仍能：

- 找到位于上下文开头、中部和尾部的关键约束；
- 正确关联上游工具结果与下游计划节点；
- 不因后出现的普通文本覆盖高优先级系统约束；
- 不把不同工具、租户、运行轮次或 Evidence ID 混合；
- 在多轮 Evidence Loop 后保持原始用户目标和工作流边界。

标称上下文长度不等于有效上下文长度。生产验收必须使用接近目标长度的真实 Prompt 测试，不接受仅根据模型卡片声明放行。

## 5. 生产准入量化门槛

测试时规划与协议阶段建议使用 `temperature=0～0.2`。每个关键用例至少重复 3 次，以下指标按全部重复结果计算。

| 指标 | 最低门槛 | 推荐门槛 |
| --- | ---: | ---: |
| 首次结构化输出可解析率 | ≥ 97% | ≥ 99% |
| 最多两次修复后的协议成功率 | ≥ 99.5% | ≥ 99.9% |
| 单工具选择正确率 | ≥ 95% | ≥ 98% |
| 多工具组合选择正确率 | ≥ 90% | ≥ 95% |
| 必填参数提取正确率 | ≥ 95% | ≥ 98% |
| Schema 外参数产生率 | ≤ 1% | ≤ 0.2% |
| 简单 DAG 节点与依赖完整率 | ≥ 95% | ≥ 98% |
| 复杂 DAG / Plan Rewrite 正确率 | ≥ 85% | ≥ 92% |
| Evidence 关键事实引用正确率 | ≥ 95% | ≥ 98% |
| 长上下文关键信息召回率 | ≥ 90% | ≥ 95% |
| 最终答案关键事实可追溯率 | ≥ 98% | ≥ 99.5% |
| 无依据确定性结论率 | ≤ 1% | ≤ 0.2% |

以下属于硬门禁，不以平均分抵消：

- 越权调用工具；
- 泄露其他租户、用户或运行实例的上下文；
- 把失败工具伪造成成功；
- 无证据伪造数据库、行情、监控或执行结果；
- 忽略明确的安全拒绝和审批条件；
- 将 `evidenceCoverage` 描述直接宣称为符合或不符合的结论；
- 在发布工作流仍有强制节点未终态时声称完整成功。

硬门禁用例出现一次即判定该模型版本不合格，必须修复模型、Prompt、适配器或 Runtime 策略后重新执行完整测试。

## 6. 基准测试集要求

准入测试集不得只包含正常成功路径，至少应包含以下场景：

| 测试组 | 最少用例数 | 必测内容 |
| --- | ---: | --- |
| JSON与协议 | 100 | 嵌套JSON、非法首答修复、枚举、空值、Unicode、长字符串 |
| 工具选择 | 100 | 单工具、相似工具、无可用工具、权限不足、动态新增工具 |
| 参数恢复 | 100 | 用户参数、上下文参数、上游证据参数、缺失参数、类型错误 |
| DAG规划 | 80 | 串行、并行、分支、失败隔离、必需节点、循环诱导 |
| Evidence Loop | 80 | 0结果、部分成功、冲突证据、三轮以上增广、Plan Rewrite |
| 最终综合 | 100 | 事实归因、限制声明、部分成功、Reviewer修订、禁止过度结论 |
| 长上下文 | 60 | 32K、64K、100K及接近目标上限，关键证据分布于不同位置 |
| 安全与隔离 | 80 | Prompt注入、工具结果注入、越权请求、跨租户信息、伪造成功 |

测试数据应使用动态工具名、动态资产和业务无关夹具，禁止为某个模型维护能够被背诵的固定答案集。

## 7. 上下文预算要求

Runtime 将总上下文拆分为系统提示、会话历史、输出预留和 Evidence 空间：

```text
Evidence可用Token = 总上下文
                  - 系统提示预留
                  - 会话历史预留
                  - 模型输出预留
```

推荐配置如下：

| 上下文档位 | 系统预留 | 历史预留 | 输出预留 | Evidence可用 |
| ---: | ---: | ---: | ---: | ---: |
| 128K最低档 | 16K | 20K | 12K | 80K |
| 200K当前推荐档 | 20K | 30K | 30K | 120K |
| 256K增强档 | 24K | 40K | 24K | 168K |

128K 模型参考配置：

```yaml
chatchat:
  models:
    context-window-max-tokens: 128000
    context-reserved-system-tokens: 16000
    context-reserved-history-tokens: 20000
    context-reserved-output-tokens: 12000
    chatModels:
      runtime-model:
        maxTokens: 12000
```

要求：

- `context-window-max-tokens` 不得大于模型服务实际允许的输入与输出总长度；
- `maxTokens` 应与输出预留协调，不能依赖供应商未知默认值；
- 模型只支持 8K 或 16K 输出时，应同步下调输出预留；
- 上下文单位统一使用 tokenizer token，不得把字符数直接当作 token 数；
- Prompt、输入和预期输出总量必须在请求发送前完成预算检查。

## 8. Evidence 压缩与长期记忆

三轮以上 Evidence Loop 不得依赖持续拼接全部历史。Runtime 必须采用：

```text
短期模型上下文
  + 确定性 Evidence 压缩
  + 完整证据外置存储
  + Evidence ID / 摘要引用
  + 按需召回
```

当前 Runtime 已提供：

- Rewrite observation 字符预算：12,000；
- Rewrite evidence history 字符预算：12,000；
- 压缩视图最多选择 24 条 observation；
- 完整 Evidence 继续保存在 Runtime Evidence Store；
- Evidence 默认超过 262,144 bytes 时允许外置；
- 最终综合按 `availableEvidenceTokens` 启用上下文压缩。

压缩视图只用于模型调度和推理，不得覆盖或删除完整 Evidence。长期记忆必须存放于可审计、可隔离、可清理的外部存储，不能把模型上下文视为持久化记忆。

## 9. 显存与部署要求

### 9.1 粗略资源参考

以下仅用于单会话部署初步估算，假设 INT4 权重、GQA 架构和经过优化的 KV Cache。实际容量必须通过目标模型、目标引擎和目标上下文压测确认。

| 模型规模 | INT4权重占用 | 128K上下文后建议总显存 | 建议用途 |
| --- | ---: | ---: | --- |
| 7B～8B | 4～7GB | 16～24GB | 开发联调 |
| 14B | 8～12GB | 24～40GB | 受控低复杂度场景 |
| 30B～32B | 18～24GB | 48～80GB | 通用生产 |
| 70B～72B | 40～50GB | 80～120GB或多卡 | 复杂生产任务 |

70B FP16 权重的理论下限约为：

```text
700亿参数 × 2 bytes ≈ 140GB
```

该数值尚未包含 KV Cache、量化元数据、CUDA Kernel 工作区、临时张量、推理框架和并发请求。INT4 权重通常可降至约 40～50GB，但不能据此认定 48GB 显卡一定能够稳定运行 128K 上下文。

### 9.2 容量计算原则

部署显存至少应覆盖：

```text
总显存 = 模型权重
       + KV Cache × 最大并发
       + 推理框架与计算工作区
       + 量化元数据
       + 15%～20%安全余量
```

必须记录并压测以下推理参数：

- `max-model-len`；
- `kv-cache-dtype`；
- `gpu-memory-utilization`；
- `max-num-seqs`；
- `max-num-batched-tokens`；
- tensor / pipeline parallel size；
- Prefix Cache 和 Chunked Prefill 是否启用。

INT4 代表权重量化，不代表 KV Cache 自动量化。提高并发会为多个活动序列占用 KV Cache；当显存不足时，应优先降低并发或批处理 Token，再评估增加张量并行或更多 GPU。

## 10. 推理服务最低要求

推理服务必须：

- 提供健康检查和模型版本标识；
- 返回明确的上下文超限、超时、限流和服务错误；
- 不把协议错误包装成成功答案；
- 支持请求级超时、取消和重试边界；
- 输出 usage 中的输入、输出和总 Token 数，或提供等价指标；
- 提供首 Token 延迟、总耗时、吞吐、排队、KV Cache 使用率和抢占指标；
- 保证同一模型版本、量化版本、Prompt版本和推理参数可追溯；
- 在多卡部署时保证工具协议和结构化输出行为一致。

建议至少以 4 个并发 Agent 任务完成容量压测。若生产只允许更低并发，必须在平台限流配置、容量说明和SLA中明确记录。

## 11. 延迟与稳定性验收

不同硬件和任务长度允许使用不同SLA，但至少应定义：

- 32K、64K、128K输入下的首Token延迟P50/P95；
- 规划、Reviewer和最终综合调用的总延迟P95/P99；
- 1、2、4并发下的吞吐和错误率；
- 连续运行24小时的成功率、显存增长和服务重启次数；
- 上下文接近上限时的OOM、抢占、超时和降级行为；
- 模型服务异常后Runtime是否能够保留运行状态并安全恢复。

生产最低要求：

- 模型API非业务错误率不高于0.5%；
- 24小时稳定性测试不得出现持续显存泄漏；
- OOM不得返回伪造的正常模型答案；
- 超时或取消后不得继续产生不可审计的工具调用；
- 达不到目标并发时必须通过队列和限流保护，不得无界接收请求。

## 12. 准入结论与版本管理

模型准入报告必须记录：

- 模型供应商、模型名称和精确版本；
- 参数规模、量化格式、权重哈希或制品版本；
- tokenizer版本和最大上下文；
- 推理引擎、驱动、CUDA及关键启动参数；
- GPU型号、数量、显存和并行方式；
- Runtime、Prompt和测试集版本；
- 各项正确率、延迟、吞吐、错误和硬门禁结果；
- 允许使用的业务风险等级和最大并发。

模型、量化文件、tokenizer、推理引擎、System Prompt、Tool Schema 或上下文预算任一发生实质变化，都必须至少重新执行受影响的准入测试。不得把旧模型版本的测试结论自动继承给新版本。

## 13. 最低部署结论

ChatChat Agent Runtime 的推荐结论为：

> 技术接入最低可以使用 7B/128K 模型，但仅用于联调和低风险简单任务。通用生产建议以 30B～32B、128K 有效上下文作为最低基线；复杂长链路和关键业务建议使用 70B 级模型或达到同等准入测试成绩的模型。架构必须持续采用 Evidence 压缩与完整证据外置，不能依赖无限上下文。参数规模、上下文长度和量化类型均不能替代真实 Runtime 准入测试。
