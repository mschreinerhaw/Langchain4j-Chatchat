# 历史报告来源版本与授权再校验方案

本方案与代码生成整改分开。B2原报告及引用保持不可变；不删字段、不改旧Hash、不取消授权检查。当前实现仍为严格再校验，尚未实施新归档版本协议。

## 四个维度

| 维度 | 判定 | 访问行为 |
|---|---|---|
| 内容版本 | 证券代码/市场/名称/类型、列表成员、行情值、观测日期、Schema或许可声明改变 | 明确SOURCE_CHANGED，旧报告标注版本变化，不伪装当前有效结论 |
| 采集刷新 | 仅声明为非版本字段的目录候选source_refreshed_at或目录last_collected_at改变 | 新版本协议可沿用旧内容版本；报告展示取得时刷新时间，并标注检查时间，不能覆盖旧时间 |
| 权限 | 当前租户/用户/Agent授权被撤回，来源访问范围收窄 | ACCESS_REVOKED，禁止正文、报告、图表和缓存泄漏；内容Hash一致也不能放行 |
| 可用性 | 已授权来源不可达/超时/删除或版本证据不可取得 | SOURCE_UNAVAILABLE或VERSION_PROOF_UNAVAILABLE，不冒充内容变化；按当前严格策略暂缓披露，不自动改用未授权来源 |

## 可实施的版本协议

新locator应同时记录`source_version_schema`、内容Hash、采集时间、取得时授权决策引用以及不可变来源快照引用。仅对工具明确声明的非内容采集字段归一化，路径白名单限于相应工具，不能递归删除全部timestamp。业务观测和行级collected_at保留版本意义。规范化算法、Hash算法、完整字段路径清单均版本化。

读取归档时先检查当前访问授权，再校验归档文件/来源快照Hash和生产任务关联；必要时读取当前来源比较内容版本。检查结果独立记录，不改写报告原件。当前内容有变化时，是否允许以“历史快照”方式披露应成为明确产品策略及权限，而不是一次bug修复中默许的行为；未定义前仍拒绝。

旧B2不能直接套用新Hash。兼容迁移必须：从原SDK已披露回执或原不可变源证据恢复候选响应；按旧算法重算且与原locator.response_hash严格一致；记录迁移证明（原引用、原Hash、证明来源Hash、新版本Hash及算法）；然后才比较当前内容。缺原回执、截断、不同任务或Hash不一致都继续拒绝。回滚时移除新兼容解析器即可恢复旧严格行为，原locator、报告与证据均不变。

## 上线前独立验收

1. 内容完全不变、仅允许的目录刷新时间变化：归档字节Hash保持一致，显示原取得时间。
2. 名称/市场/候选成员、行情值或业务观测时间变化：严格标记内容变化；不能误当刷新。
3. 撤权：即使快照已缓存仍拒绝所有相关披露。
4. 来源不可用：与内容变化分别分类，不能报告“没有行情”。
5. 旧引用缺迁移证明或证明Hash不符：继续拒绝；禁止改写旧locator制造通过。
6. B2/D3原文件分别复读，记录HTTP结果、字节数、SHA和授权/版本状态；不得以新报告替代历史复读。

本轮计算/报告修复不依赖放宽上述规则。实施此协议涉及持久化版本证明与历史披露产品语义，应独立提交并进行上述真实回归；仅提出方案不算B2归档问题已解决。
