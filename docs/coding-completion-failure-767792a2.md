## 是否可以安全恢复

**原权限与原预算下不能继续推理或执行。** 原期限已经过去，历史第六轮也缺少真实终止证明。不能回填一张“现在推测当时已停止”的证明，更不能清空预留、延长期限、换 taskId 或重跑 Python 来绕过核对。现在可以继续只读查询原操作及供应商回执；若获得真实历史证明，可对原操作做核对和安全终止，仍不产生新的计算授权。

本次修复为未来的 Java 回调失败在事实发生时归档本地终止证据，保留未知供应商用量，并只在原期限内、原操作全部有 stop proof 时恢复同一 task 的 SDK checkpoint。对已经过期且证据缺失的原案例，保持原身份和明确阻塞原因是正确行为。

## 如何降低再次发生的概率

每轮可见实际剩余预算与未知预留，动态完成分配提示尽早形成可验证结果；原生压缩保留有界技术错误记忆，避免源码定位后丢失修复原因；已验证资产持续归档，后续失败不抹掉成果；每次真实 Java 回调异常留下本地终止证据，避免只能等到全任务期限。全部机制复用原 Runtime/Cline 状态机，没有股票业务硬编码和额外规划模型。

预留机制能给本例的修复和验证提供更明确的资源信号，但不能保证模型生成正确代码，也不能消除真实供应商超时。该任务在诊断时没有有效成果、预算内成功率与有效交付率均为 0；每成功任务 Token/调用为 null，不能除以 0 或假报下降。性能提升仍需相同任务、相同真实模型与预算的配对实验；本病例不重放业务来制造验收结果。
