# DAG 修复准入

原来的补证策略把执行失败直接视作“有可探索路径”，随后通过全局 Rewriter 重写计划。固定工作流还会重新校正生成的图；SQL、连接或持久化故障本身不会因此改变。

现在在 `InterpretationAnalysisSession.refinementGate`、调用重写模型之前做确定性准入：

- `INVALID_PLAN` 可进入一次结构修复。再次失败直接结束修复。
- 普通执行失败不能单独成为重写依据。
- 补证动作必须能够解析到当前可用的具体工具，且该工具在本次全部执行轮次中尚未尝试。
- 授权未满足时不启动修复。
- 不满足条件时记录 `refinementAdmission`、`refinementStopReason`，关闭补证循环，保留已有证据和失败信息进行最终分析。

`dag_repair` 事件现在只代表无效计划的结构修复。取得新证据的计划扩展不再被描述为 DAG 修复。没有修改模型调用超时，也没有在 Runtime 中加入业务名称或 SQL 特例。

边界：这是保守准入，并非通用故障自动修复器。同一个工具通过新参数补证，目前不会仅凭模型建议重新开启外层全局重写；节点内部已有的执行重试、检查点恢复机制继续工作。恢复同工具补证需要进一步提供经过验证的参数变更或数据状态变更证明，不能退回“失败就再试”。

验证：7 个测试类、19 项测试通过；包含主链路在执行失败时跳转 FINALIZE 且不调用重写模型的测试，以及图执行、增量修复和结果复用的回归测试。
