# MCP 工具发布与权限管理视觉统一

在 `feature/unified-management-workspaces` 上继续整改，保留 `2.2.0-rc2` 和原基线 Tag。本次仅修改用户端展示与交互，继续调用统一权限与工具发布接口，不新增授权存储、发布服务或数据库迁移。

## 现状与修复

| 问题 | 修复 |

| 资源分类“其他资源”含义不清 | 名称统一为“领域技能”，保留既有技能与查询服务范围规则 |

## 交互与权限

发布页先选择逻辑工具，再选择版本，按“版本概览 / 工具定义 / 测试与记录”操作。保存新草稿、校验、真实合约测试、发布、下线、回滚仍使用原 `/tool-publications` API，依次满足原生命周期约束。

创建下一版本时复制定义，不修改源版本。角色、能力与逻辑身份保持稳定。切换角色/能力清空原模板选择，忽略过期的异步目录结果；原模板失去授权时明确提示，不能静默扩大模板范围。保存和测试的 JSON 错误保留输入并给出修正提示；新建工具会清空上一工具的结构和测试输入。未保存变更离开前确认；下线和回滚二次确认。

内部基础能力的隐藏只属于管理目录投影。按第一方 provider 标识与明确的固定能力标识分类，保留同一 provider 发布的业务工具，保留其他 provider 的工具，保留未注册但仍有显式规则的业务工具以便核查。成功取得当前注册目录时，隐藏没有规则的失效登记条目。没有按“ChatChat MCP Server”文本进行模糊删除，也没有删除历史权限数据。

Runtime 和 MCP 对业务工具、模板及数据范围继续执行统一授权；内部服务连接无需在此创建单独授权。现有规则、拒绝优先、角色/用户/租户与数据范围校验保持原样。工具发布成功不会赋予新的数据访问权限。

## 部署与回滚

`deploy-publication-workspace-ui.py` 只替换 API 镜像，部署前检查空闲任务、核验 JAR、保存 API 数据库快照与 compose/环境文件，记录旧不可变镜像标识和运行包哈希。旧镜像、旧发布包与此前完整备份保留；此次无需重复备份未变更的 MCP 服务和运行 JAR。构建后删除本次镜像构建 JAR 副本，解包后删除本次传输副本，以控制验收环境磁盘占用。

上线后比对角色权限、用户角色关系、工具授权、资源授权和 MCP 模板绑定指纹，检查实际运行包哈希。失败自动恢复旧 compose/环境与 API 镜像，刷新代理；不执行数据库回滚或改写原导航。
